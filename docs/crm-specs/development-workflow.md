# ElMiCo CRM - Spec driven development με TDD

Η παρούσα διαδικασία είναι υποχρεωτική για την υλοποίηση της έκδοσης 1.6 των specs.
Το spec ορίζει την αναμενόμενη συμπεριφορά και τα tests καθοδηγούν την υλοποίησή της σε μικρά βήματα.
Οι λειτουργικές απαιτήσεις και οι εγκεκριμένες επιχειρησιακές αποφάσεις παραμένουν αμετάβλητες.

**Κύκλος ανά συμπεριφορά**

```text
Απαίτηση και κριτήριο αποδοχής
    -> μικρό εκτελέσιμο test
    -> RED: παρατήρηση αναμενόμενης αποτυχίας
    -> GREEN: υλοποίηση που ικανοποιεί τη συμπεριφορά
    -> REFACTOR: βελτίωση δομής με πράσινα tests
    -> έλεγχος ολοκληρωμένης ροής και ενημέρωση αποδεικτικών
```

1. Διάβασε την αντίστοιχη απαίτηση, το σενάριο AT και τον σχετικό τεχνικό κανόνα.
2. Επίλεξε μία μικρή συμπεριφορά και γράψε πρώτα το test που αποδεικνύει το αναμενόμενο αποτέλεσμα.
3. Εκτέλεσε το test και επιβεβαίωσε ότι αποτυγχάνει εξαιτίας της λειτουργίας που λείπει ή του bug που αναπαράγεται.
4. Υλοποίησε μόνο ό,τι χρειάζεται για τη συγκεκριμένη συμπεριφορά, διατηρώντας τους κανόνες ασφάλειας και ακεραιότητας του spec.
5. Εκτέλεσε το test και τα επηρεαζόμενα γειτονικά tests μέχρι να περάσουν.
6. Βελτίωσε ονόματα, δομή και επαναχρησιμοποίηση χωρίς αλλαγή συμπεριφοράς και ξανατρέξε τα σχετικά tests.
7. Επανάλαβε για το επόμενο όριο, αποτυχία ή επιχειρησιακό παράδειγμα της ίδιας ροής.
8. Ολοκλήρωσε τη συμπεριφορά με τον κατάλληλο integration ή E2E έλεγχο και καταγραφή αποτελέσματος.

Δεν γράφονται πρώτα όλα τα tests όλου του έργου ούτε όλος ο κώδικας ενός feature πριν από το πρώτο test.
Κάθε πακέτο W χωρίζεται σε μικρές συμπεριφορές με τον παραπάνω κύκλο.
Η απλή ύπαρξη test που περνά μετά την υλοποίηση δεν αποδεικνύει ότι εφαρμόστηκε TDD.

**Έγκυρο RED και υποδομή δοκιμών**

Η αποτυχία πρέπει να σχετίζεται με το προβλεπόμενο αποτέλεσμα του test.
Σφάλμα σύνδεσης test βάσης, λανθασμένο import, μη διαθέσιμος browser ή προβληματικό fixture δεν θεωρείται απόδειξη ότι λείπει η ζητούμενη συμπεριφορά.
Για νέα μονάδα μπορεί να προστεθεί το ελάχιστο κενό περίβλημα που απαιτεί ο runner, χωρίς να υλοποιηθεί εκ των προτέρων η επιχειρησιακή λογική.
Η υποδομή ελέγχεται πρώτα με μικρό smoke test ώστε να διακρίνεται η αποτυχία προϊόντος από την αποτυχία περιβάλλοντος.

Τα scripts προετοιμασίας, ο test runner και τα fixtures δεν απαιτούν τεχνητά αποτυχημένα tests όταν απλώς εγκαθιστούν εργαλεία.
Η απαίτηση RED ισχύει για την υλοποίηση ή τη διόρθωση συμπεριφοράς του CRM.
Οι αλλαγές τεκμηρίωσης και χειροκίνητες ρυθμίσεις Plesk επαληθεύονται με ελέγχους συνέπειας ή το πραγματικό runbook, όχι με προσχηματικά unit tests.

**Υφιστάμενος κώδικας και διορθώσεις**

Authentication, ασφάλεια και τα γνωστά λειτουργικά bugs διορθώνονται και ελέγχονται πριν αρχίσει η ανάπτυξη των νέων features.
Η μετάβαση επιτρέπεται μόνο με καταγεγραμμένο baseline PASS G01, όπως ορίζεται στο [tasks.md](tasks.md).
Αυτή η φάση χρησιμοποιεί την ίδια διαδικασία TDD και δεν είναι ανεξέλεγκτο refactoring πριν από τα tests.

Για bug fix προηγείται αναπαραγωγή από πραγματικό browser ή HTTP ροή όσο γίνεται πιο κοντά στον τελικό χρήστη.
Η αναπαραγωγή μετατρέπεται σε επαναλήψιμο αποτυχημένο E2E ή HTTP integration regression test πριν από την αλλαγή παραγωγικού κώδικα.
Στη συνέχεια προστίθενται μικρότερα tests στη μονάδα που θα αλλάξει, όπου αυτά κάνουν τη διάγνωση και την κάλυψη ορίων σαφέστερες.

Πριν από refactoring σε legacy κώδικα μπορούν να προστεθούν characterization tests που καταγράφουν την ήδη σωστή συμπεριφορά και περνούν από την αρχή.
Αυτά προστατεύουν την παλινδρόμηση και δεν αντικαθιστούν το RED test για τη νέα ή διορθωμένη συμπεριφορά.
Για γνωστό κενό authentication, το test περιμένει την ασφαλή απόκριση και αρχικά αποτυγχάνει επειδή ο υπάρχων κώδικας αποκαλύπτει δεδομένα.
Δεν κλειδώνουμε την ευπάθεια ως επιθυμητή συμπεριφορά για να διατηρήσουμε πράσινη τη σουίτα.

**Κατανομή tests**

| Επίπεδο | Τι καλύπτει | Παραδείγματα από τα specs |
|---|---|---|
| Unit | Καθαρούς κανόνες και όρια με ελεγχόμενες εισόδους. | Parsing ποσών, τελευταία ημέρα μήνα, πρώτη επηρεαζόμενη περίοδος, επιλογή ιστορικής έκδοσης και όριο αδράνειας. |
| Integration | Πραγματική αποθήκευση, συναλλαγές και συμβάσεις PHP/HTTP. | Migrations, snapshots, CSRF, ρόλοι, counters σύνδεσης, rollback και μοναδικότητα occurrence στη MariaDB. |
| E2E | Πραγματικές ροές χρήστη με browser στο `/crm/`. | Login, καταχώριση εργασίας, επιλογή μέσου, αλλαγή κανόνα και εμφάνιση ποσών σε mobile/desktop. |
| Έλεγχοι hosting και ανθρώπινη QA | Πραγματική διαμόρφωση και αποτελέσματα που δεν αποδεικνύονται μόνο τοπικά. | Cookie σε HTTPS, Plesk scheduler, backup/restore, PDF/Excel σε συμβατή εφαρμογή και οπτική επιθεώρηση. |

Ένα σενάριο AT μπορεί να απαιτεί πολλά tests σε διαφορετικά επίπεδα.
Δεν χρειάζεται κάθε αριθμητικός ή ημερολογιακός συνδυασμός να επαναλαμβάνεται σε browser αν καλύπτεται ακριβώς σε unit test και υπάρχει E2E κάλυψη της πραγματικής ροής.
Τα κρίσιμα όρια πρόσβασης ελέγχονται με πραγματικά HTTP αιτήματα ακόμη και αν υπάρχει ξεχωριστό unit test του guard.

**SET agent και ανεξάρτητη QA**

Στο W01 χρησιμοποιείται ο SET agent του `.codex/agents/set.toml` για στρατηγική, επιλογή κατάλληλου test stack, fixtures και υποδομή, όταν το περιβάλλον υποστηρίζει τον custom agent.
Στα επόμενα πακέτα η ανάθεσή του ορίζει ρητά αν καλύπτει συγγραφή tests, έλεγχο ή και αλλαγές παραγωγικού κώδικα.
Μια ανάθεση μόνο ελέγχου ή tests δεν εξουσιοδοτεί αυτόματα αλλαγή της λειτουργίας του προϊόντος.
Ο κύριος agent παραμένει υπεύθυνος για εξαρτήσεις, εφαρμογή specs και συνοχή της υλοποίησης.
Αν ο custom agent δεν είναι διαθέσιμος, οι οδηγίες του `.codex/agents/set.toml` ακολουθούνται απευθείας και η έλλειψη δυνατότητας καταγράφεται.
Τα G01 και W09 εξακολουθούν να απαιτούν ανεξάρτητο έλεγχο με ρητή ανάθεση επιθεώρησης, χωρίς αυτόματες διορθώσεις.
Ο agent που υλοποίησε μια αλλαγή δεν είναι η μοναδική αρχή που την χαρακτηρίζει PASS.

**Υποδομή tests του W01**

Ανίχνευσε πρώτα το λειτουργικό σύστημα και επίλεξε την αντίστοιχη μέθοδο.
Σε macOS δοκιμάζουμε με native PHP και MariaDB.
Σε Linux δοκιμάζουμε μέσω Docker Compose με PHP και MariaDB containers.

Σε macOS χρησιμοποιούνται native PHP, MariaDB και Composer, χωρίς Docker.
Πριν από την εργασία ελέγχονται η διαθεσιμότητα και οι εκδόσεις τους, τα απαιτούμενα PHP extensions και η σύνδεση PHP με MariaDB.
Η MariaDB ξεκινά όταν χρειάζεται και η τοπική ανάπτυξη χρησιμοποιεί ξεχωριστή βάση και χρήστη CRM.
Τα αυτοματοποιημένα tests χρησιμοποιούν απομονωμένη test βάση ή προσωρινό test-owned data directory.

Σε Linux η αφετηρία είναι το υπάρχον Docker configuration του repository, με συμβατότητα PHP 8.3 και MariaDB 10.11.
Τα tests χρησιμοποιούν ξεχωριστή test βάση ή απομονωμένο Compose project με test-owned volumes και credentials.
Το test περιβάλλον εγκαθιστά τα απαραίτητα development dependencies, καθώς το production Dockerfile εκτελεί Composer με `--no-dev`.
Οι τοπικές ρυθμίσεις δεν αποδεικνύουν ταυτόσημη διαμόρφωση στο Otenet.

Το W01 πρέπει να παραδώσει τα παρακάτω πριν από αλλαγές συμπεριφοράς:

- Test περιβάλλον που εξυπηρετεί πραγματικά την εφαρμογή στο `/crm/` με τις σωστές nested διαδρομές και ρυθμίσεις cookies.
- Ελεγχόμενη HTTPS δοκιμή για τις ιδιότητες ασφαλούς session cookie, χωρίς χαλάρωση της παραγωγικής πολιτικής για να περάσουν τα tests.
- Εγκατάσταση των απαιτούμενων development dependencies στο test περιβάλλον, χωρίς εισαγωγή τους στο production release.
- Σε Linux, ξεχωριστό test service, stage ή τεκμηριωμένη override διαδικασία και απομονωμένη test βάση ή Compose project.
- Σε macOS, απομονωμένη test βάση ή προσωρινό test-owned data directory, χωριστά από τη βάση ανάπτυξης.
- Έλεγχο του πραγματικού host και ονόματος βάσης πριν από reset, import ή cleanup, με άρνηση εκτέλεσης αν δεν επιβεβαιώνεται ο αναμενόμενος test στόχος.
- Προστασία των development και production βάσεων και, στο Linux, των συνηθισμένων development `db_data` και `app_vendor` volumes από διαγραφή ή αντικατάσταση.
- Ανάγνωση υπάρχοντος `.env` χωρίς αντιγραφή του `.env.example` πάνω σε υπάρχον αρχείο και χωρίς κληρονομιά της συνηθισμένης βάσης ως test στόχου.
- Αναπαραγώγιμες, πραγματικά εκτελεσμένες εντολές για focused unit, integration και E2E checks στο `implementation-status.md`.

Δεν καταγράφονται credentials σε εντολές αποδεικτικών ή logs.
Η εγκατάσταση runtimes από μόνη της δεν ολοκληρώνει το W01 και δεν αποτελεί PASS της εφαρμογής.
Δεν θεωρείται δεδομένο ότι υπάρχει ήδη runner ή test command και δεν αναφέρονται μη δοκιμασμένες εντολές ως λειτουργικές.
Η παραγωγική εγκατάσταση εξακολουθεί να χρησιμοποιεί μόνο τα απαιτούμενα production dependencies.

**Συμβάσεις και test seams**

Τα νέα tests ονομάζονται με την παρατηρήσιμη συμπεριφορά και αναφέρουν στο test name, metadata ή docblock τους σχετικούς κωδικούς απαίτησης και AT.
Η έκθεση εκτέλεσης κρατά την αντιστοίχιση απαίτηση -> σενάριο AT -> πραγματικό test ή τεκμηριωμένο χειροκίνητο βήμα.
Δεν ελέγχονται ιδιωτικές μέθοδοι, ακριβές SQL strings ή εσωτερική σειρά helper κλήσεων όταν αυτά δεν αποτελούν απαίτηση.

Η λογική ημερομηνιών και λήξης συνεδρίας δέχεται ελεγχόμενο clock ή ρητή τιμή χρόνου.
Τα tests δεν χρησιμοποιούν μεγάλες αναμονές ή αλλαγή του πραγματικού server clock.
Οι καθαροί ημερολογιακοί κανόνες δεν εξαρτώνται από database connection ή browser session.
Όλα τα integration tests και τα tests SQL, συναλλαγών, constraints και concurrency χρησιμοποιούν πραγματική MariaDB, χωρίς SQLite ή mock που προσποιείται την κρίσιμη συμπεριφορά της βάσης.
Ταυτόχρονες εκτελέσεις συγχρονίζονται με ελεγχόμενο σημείο έναρξης, αντί να στηρίζονται στην τύχη ή σε αυθαίρετο sleep.
Κάθε test έχει απομονωμένα δεδομένα και δεν εξαρτάται από τη σειρά εκτέλεσης.
Δεν γίνονται tests που γράφουν σε παραγωγική βάση ή περιέχουν πραγματικά δεδομένα πελατών.

**Αποδεικτικά ανά αλλαγή**

Κάθε ολοκληρωμένη αλλαγή καταγράφει τα παρακάτω στο PR ή σε συνοπτικό execution record του CRM repository:

```text
Απαιτήσεις: REC-04
Σενάρια: AT-31
Tests: <πραγματικά ονόματα ή αρχεία tests>
RED: <εντολή και παρατηρημένη αποτυχία πριν από την υλοποίηση>
GREEN: <ίδια εντολή και πραγματικό επιτυχές αποτέλεσμα>
REFACTOR: <αλλαγή δομής, αν χρειάστηκε, και σχετικοί επανέλεγχοι>
Regression / E2E: <εντολές και αποτελέσματα>
Χειροκίνητη QA: <αποτέλεσμα ή αιτιολογημένο δεν εφαρμόζεται>
```

Δεν απαιτείται ξεχωριστό commit με αποτυχημένα tests ή διατήρηση κόκκινης κύριας CI pipeline.
Απαιτείται να έχει παρατηρηθεί το RED πριν από την υλοποίηση και να καταγραφεί ειλικρινά.
Αν κάποιο βήμα δεν εκτελέστηκε, αναφέρεται ως μη εκτελεσμένο και δεν κατασκευάζεται εκ των υστέρων ιστορικό TDD.
Τα παραδείγματα και τα κενά templates δεν αποτελούν αποδεικτικά εκτέλεσης.

**Definition of Done ανά συμπεριφορά**

- [ ] Η απαίτηση και το αντίστοιχο σενάριο AT είναι σαφή και ενημερωμένα.
- [ ] Παρατηρήθηκε η σχετική αποτυχία πριν από την αλλαγή συμπεριφοράς.
- [ ] Τα ουσιώδη επιτυχή, αποτυχημένα και οριακά παραδείγματα καλύπτονται στο κατάλληλο επίπεδο.
- [ ] Η υλοποίηση περνά τα νέα tests και τους σχετικούς ελέγχους παλινδρόμησης.
- [ ] Έχει γίνει refactoring όπου χρειάζεται με πράσινα tests.
- [ ] Η πραγματική ροή καλύπτεται με HTTP ή browser όπου απαιτείται.
- [ ] Η αντιστοίχιση απαίτησης, AT και tests είναι καταγεγραμμένη.
- [ ] Δεν απομένει σχετικό κρίσιμο ή υψηλής σοβαρότητας εύρημα.

Η κάλυψη κώδικα είναι συμπληρωματικό μέτρο και δεν αντικαθιστά ούτε το RED ούτε τα κριτήρια αποδοχής.
Οι απαιτήσεις τελικής ανεξάρτητης QA, ανθρώπινης επιθεώρησης και πραγματικού post-deploy ελέγχου εξακολουθούν να ισχύουν.
